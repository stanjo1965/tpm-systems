플랫폼은 네 계층으로 나뉩니다

아래 층이 흔들리면 위층이 전부 흔들립니다. 그래서 순서가 있습니다.

LAYER 01Channel채널 · 쓰는 사람이 닿는 면
웹 화면모바일 앱현장 바코드외부 연계 창구

같은 데이터를 보는 사람에 맞춰 다르게 보여 줍니다. 앱은 웹 화면을 그대로 쓰는 하이브리드라, 서버가 바뀌면 앱을 다시 깔지 않아도 화면이 함께 바뀝니다.

LAYER 02Operation업무 · 매일의 일이 지나는 곳
Order 오더Dispatch 배차·운행Warehouse 창고Settlement 운임·정산

네 구간이 끊기지 않고 한 여정으로 이어집니다. 전부 한 번에 도입하지 않아도 됩니다 — 필요한 구간만 떼어 먼저 쓰고 뒤에 이을 수 있습니다.

LAYER 03Intelligence지능 · 쌓인 데이터가 판단을 돕는 곳
질의배차·재고 추천예외 감지업무 에이전트

업무 계층에 데이터가 쌓여야 비로소 서는 층입니다. 근거와 후보는 AI 가 내고 결정은 담당자가 합니다. 승인한 결정이 다시 쌓여 다음 추천이 좋아집니다.

LAYER 04Foundation기반 · 위 세 층이 딛고 선 곳
기준정보연계업무 온톨로지승인·보안

화면보다 먼저 보는 곳입니다. 코드 체계가 어긋나거나 권한이 헐거우면 위층에서 아무리 좋은 화면을 만들어도 숫자를 믿을 수 없습니다.

한 여정이 지나는 다섯 구간

구간마다 쓰는 사람과 다루는 데이터가 다릅니다. 플랫폼은 그 사이가 끊기지 않게 잇습니다.

01 ORDER

Order오더

채널별 주문 수집 → 표준화·검증 → 재고/센터 할당 → 출고·운송 지시

  • 원주문과 분할 주문을 한 이력으로
  • 납기·우선순위와 주문 변경 관리
  • 취소·반품·클레임까지 같은 흐름에서
쇼핑몰 · ERP · 고객센터 연계

현장 · 가구 홈쇼핑 물류채널마다 양식이 다른 주문을 한 오더 체계로 모아 센터에 할당하고, 분할·취소·반품까지 같은 이력으로 따라갑니다.

02 DISPATCH

Dispatch배차·운행

운송 의뢰 접수 → 차량 조건 확인 → 배차·수락 → 상차·운행·하차 → 인수 확인

  • 화주·거래처, 차량·기사 정보
  • 노선·운임표와 배차 이력
  • 운송 상태와 증빙을 현장에서 바로
GPS · 지도 연계

현장 · 수출입 컨테이너 운송내수 LCL 과 수출입 FCL 오더를 한 배차판에서 받고, 데머리지 잔여일을 경고로 띄워 반납을 놓치지 않게 합니다.

03 WAREHOUSE

Warehouse창고

입고 예정 → 검수·적치 → 주문 할당 → 피킹·검수·포장 → 출고 확정

  • 품목·바코드·로트 단위 관리
  • 가용·보류 재고와 로케이션
  • 재고 이동·조정·실사와 작업자 이력
OMS · TMS · 택배 연계

현장 · 가구 홈쇼핑 창고대형·다품목 가구를 부피와 품목 특성에 맞춘 로케이션으로 두고, 재고 위치와 작업자 이력을 실시간으로 봅니다.

04 SETTLEMENT

Settlement운임·정산

인수 확인 → 운임 확정 → 정산 → 손익 확인

  • 미수·미지급과 가맹 수수료
  • 운임 조건별 원가와 수익성
  • 전화·수기 없이 증빙으로 정산
세금계산서 · 회계 시스템 연계

현장 · 화물운송 가맹망가맹점별 매출과 수수료를 증빙으로 정산하고 세금계산서까지 연결해, 전화와 수기 대조를 없앴습니다.

05 INTELLIGENCE

Intelligence분석·AI 에이전트

데이터 축적 → 후보·근거 제시 → 담당자 승인 → 결정 이력 축적

  • 차종·거리·시간·공차·기사 이력을 함께 분석
  • 배차 후보와 예상 지연, 수익성 판단
  • AI 가 근거를 내고 사람이 승인합니다
결정 이력으로 규칙을 계속 고칩니다

현장 · 제조 그룹 경영 질의「지난주 정지 시간이 왜 늘었나」처럼 사람 말로 물으면 운영 데이터에서 근거와 함께 답합니다.

플랫폼을 떠받치는 다섯 가지

구간을 잇는 것은 화면이 아니라 그 아래의 기반입니다.

01 MASTER DATA

Master Data기준정보

거래처·품목·차량·기사·창고·운임표를 한 곳에서 정의하고, 모든 모듈이 같은 코드를 가져다 씁니다. 기준이 어긋나면 그 뒤의 집계가 전부 어긋납니다.

  • 한 번 정의하면 모든 화면이 같은 값을 봅니다
  • 바뀐 이력과 그 코드가 쓰이는 곳을 함께 추적
  • 회사·사업장별로 보이는 범위를 나눠 관리

사례 · 제조 그룹 네 곳한 시스템에 네 그룹을 올리면서 공통 코드와 회사별 경계를 갈랐습니다. 본사는 전부 보고 계열사는 자기 것만 봅니다.

02 INTEGRATION API

Integration연계

쇼핑몰·ERP·회계·GPS·택배·세금계산서와 데이터를 주고받습니다. 상대 시스템을 바꾸지 않고 옆에 붙이는 방식이라 운영을 멈추지 않습니다.

  • 표준 API 와 엑셀·CSV 양쪽을 모두 받습니다
  • 실패한 연계는 버리지 않고 재처리 대기열로
  • 주고받은 원문을 남겨 나중에 대조합니다

사례 · 주문·재고 수집 자동화물류사와 오픈마켓의 주문을 사람 손 없이 받아 적재하고, 실패한 건은 버리지 않고 다시 집어 넣습니다.

03 BUSINESS ONTOLOGY

Ontology업무 온톨로지

표와 컬럼이 아니라 「오더」와 「배차」와 「재고」가 서로 무엇인지를 관계로 적어 둡니다. 업무 지식이 담당자의 머리가 아니라 구조에 남습니다.

  • 업무 용어와 데이터 구조를 잇는 사전
  • 규칙과 제약을 문서가 아니라 구조로 보관
  • 시스템을 바꿔도 지식은 그대로 남습니다

사례 · 소스가 없는 레거시만든 사람도 설계서도 없는 시스템에서 화면과 응답 데이터만으로 업무 규칙을 복원해 구조로 남겼습니다.

04 APPROVAL & SECURITY

Approval & Security승인·보안

역할마다 보이는 범위가 다르고, 중요한 변경은 승인을 거칩니다. 누가 언제 무엇을 바꿨는지가 남아야 운영 사고를 되짚을 수 있습니다.

  • 역할·회사 단위 접근 제어와 로그인 표준
  • 단가·정산처럼 민감한 변경은 승인함을 거쳐
  • 변경 이력을 감사 기록으로 보관

사례 · 멀티컴퍼니 기반 모듈회사 경계·기능 권한·로그인 표준을 공통 모듈로 한 번 만들어 모든 제품이 상속합니다. 제품마다 따로 만들지 않습니다.

05 AGENTIC AI

Agentic AI업무 에이전트

반복 업무는 에이전트가 대신 수행하고, 판단이 필요한 일은 근거와 후보를 함께 올립니다. 정하는 사람은 끝까지 담당자입니다.

  • 사람 말로 묻고 표·그래프로 답을 받습니다
  • 배차·재고·정산 후보를 근거와 함께 제시
  • 승인한 결정이 쌓여 다음 추천이 좋아집니다

사례 · 상용 RPA 자체 이관구독형 RPA 열두 종을 자체 코드로 옮겨 예약 수행과 실패 추적까지 플랫폼 안에서 돌립니다.
